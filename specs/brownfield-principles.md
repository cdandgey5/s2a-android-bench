# Spec: Brownfield principles the S2A orchestrator implements

Researched 2026-10-16 from the sources listed at the end. Each principle is either **enforced**
by an orchestrator gate, **encoded** in a stage prompt, or **deferred** with a reason. D-016:
no stage exists that no principle motivates, and no principle below is silently dropped.

## Cross-cutting principles → where they live

| # | Principle | Supported by | Enforced / encoded in S2A |
|---|---|---|---|
| P1 | **Understand before changing; scope the documentation to the change.** Build a factual map of the codebase first, but document only what the change needs — "do not make 'document the entire system' your first feature". | BMAD brownfield, Spec Kit existing-projects, Fowler legacy-modernization, Feathers, Claude Code best practices, Aider repo map | `map` stage (≤ 400 lines, facts with file evidence, central files ranked by references, commands proven by running them — **gate `map_test_command_runs`**); `locate` stage scopes to the ticket. |
| P2 | **Precision over volume in context.** Hierarchical localization (repo → files → symbols → lines), just-in-time retrieval, sub-stages that return condensed summaries; more context lowered resolution in FEA-Bench. | Anthropic context engineering, Agentless, FEA-Bench, Aider, SWE-agent | Every stage runs in a **fresh session** with only its inputs; `render.py` caps each placeholder (map sections by heading, diff ≤ 60 kB); `locate` returns a ranked, condensed analysis; `implement` gets one task + `progress.md`, not the transcript. |
| P3 | **Spec the change, not the system; agree "done" before any code; mark unknowns explicitly.** | Spec Kit, Kiro, Claude Code best practices, Anthropic harness-design ("sprint contract") | `intake` ("done when", unknowns) and `spec` (EARS acceptance criteria with a verification method each — **gate `every_criterion_has_verification`**); interactive mode pauses for approval; autonomous mode records assumptions instead of guessing silently. |
| P4 | **State unchanged behaviour and compatibility boundaries explicitly.** Hyrum's law: every observable behaviour is depended on; a bugfix spec names what SHALL CONTINUE TO work. | Kiro bugfix specs, Hyrum's law, BMAD, Spec Kit, Feathers | `spec` has a mandatory **"Unchanged behaviour"** section and **"Compatibility constraints"**; `verify` treats any behaviour change outside the spec as a defect. |
| P5 | **Reproduce or characterize first, and validate the test itself.** A fail-to-pass test must fail on the original code for the right reason; one test per behavioural facet (a single repro test yields partial patches); characterization tests pin legacy behaviour before refactoring. | Agentless, SWE-Doctor, Claude Code best practices, Kiro, Spec Kit (test-first), Feathers | `reproduce` stage — **gate `repro_tests_behave`** runs the tests: bug → fail with an assertion (not a compile error), refactor → pass, feature skeleton → compiles; prompt asks for one test per "done when" item; after implementation **gate `repro_tests_pass_from_fixing_task`**. |
| P6 | **Run a relevant regression subset as a gate, every step.** Pruning the suite to the relevant tests improved resolution; every touched legacy module needs tests. | TestPrune, Agentless, BMAD, Android testing strategies | `locate` lists existing tests touching the candidates; `implement` per-task gate runs the task's tests; after all tasks **gate `affected_modules_tests_pass`**, evaluated **relative to a cached baseline at `base_commit`** (brownfield repos often have pre-existing failures; only newly failing tests count); `verify` runs the affected modules' full unit tests and reports failures outside the change. |
| P7 | **Small, atomic, verified steps; preparatory refactoring separate from behaviour change.** "Make the change easy, then make the easy change"; ≤ ~200 changed lines per step; one issue per change; sprout/wrap over editing large legacy methods in place. | Anthropic harnesses, Google SWE book ch. 9 + small CLs, Fowler preparatory refactoring, Feathers (sprout/wrap/seams) | `plan` prompt: small tasks (≤ ~200 lines), preparatory refactoring first as its own task, approach ∈ sprout/wrap/modify; `implement` commits **one task per fresh session**; **gate `every_criterion_covered`**. |
| P8 | **Independent evaluator in a fresh context, with hard thresholds and evidence — never self-grading.** Agents "skew positive when grading their own work"; a skeptical standalone evaluator is more tractable than a self-critical generator; reviewer sees only diff + criteria and flags correctness/requirement gaps. | Anthropic harness-design, Claude Code best practices, Building effective agents, context engineering | `verify` stage: fresh session, read-only tools, sees ticket + spec + diff + repro, must give per-criterion PASS/FAIL with evidence; **any FAIL ⇒ REJECT, derived by the orchestrator (`verdict_consistent`), not trusted to the model's last line**; tree reset after; the `fix` stage runs under the same gates as implementation; verifier prompt calibrated with scored examples on the dev set (Phase 6 step 18). |
| P9 | **Deterministic guardrails on edits and tools.** Reject edits that fail lint; hooks/gates decide, not the model's claim; strict, actionable error messages. | SWE-agent, Claude Code best practices (Stop hooks), Writing tools for agents, FEA-Bench | Gates run commands themselves (compile, tests, path existence) and never trust "tests passed" text; gates **render commands from profile templates + `plan.json` fields and never execute an agent-written command string**; **gate `no_weakened_tests`** (diff rule); optional lint gate when the map-time lint timing is fast; gate failures feed the retry prompt as `{{previous_attempt_errors}}`. |
| P10 | **Bounded loops; fail fast; reset context after repeated failure.** Success after one failed edit drops sharply; after two failed corrections clear context and re-prompt. | SWE-agent, Claude Code best practices, Building effective agents, harness-design | `fix_loops: 2`, `implement_task_retries: 2`, each retry in a **fresh session**; a task that still fails stops `implement` and the run proceeds to `verify` (which will REJECT) and `report` with the failed task named; budgets end the run with exit 4. |
| P11 | **Persist state in files across fresh sessions.** Progress notes, a feature/task list whose status only the harness flips, git log as memory; each session starts by reading progress and checking the baseline. | Anthropic harnesses, context engineering, harness-design | `state.json` (orchestrator-owned; agents never edit it), `progress.md` (appended per task, given to every implement session), one git commit per task, `s2a resume`; implement procedure step 0 = read progress, run the task's test command once to confirm the baseline. |
| P12 | **Simplest harness that works; prove each component is load-bearing by removing it.** | Building effective agents, harness-design, context engineering | Benchmark ablations `--skip map`, `--skip verify`, `--skip reproduce`; `pipeline.yaml` has no stage that a principle above does not motivate. |

## Source-specific recommendations and how each is handled

| Source | Recommendation | Handling |
|---|---|---|
| Anthropic, *Building effective agents* | Prompt chaining with programmatic gates for predefined steps; evaluator–optimizer only with clear criteria and a max-iteration stop; absolute file paths in tool calls. | Orchestrator = prompt chain + gates; verify/fix loop capped; preamble asks for absolute paths. |
| Anthropic, *Effective harnesses for long-running agents* | Initializer writes progress file + initial commit; feature list in JSON where only the status flips; one feature at a time; each session reads progress + git log and runs a basic check before new work; "it is unacceptable to remove or edit tests"; end every session in a clean mergeable state. | `intake` + `map` act as initializer; `plan.json` statuses are orchestrator-owned; one task per session; implement step 0 baseline check; `no_weakened_tests` gate; commit per task. |
| Anthropic, *Effective context engineering* | Preload only stable essentials; hand stages identifiers and retrieve just-in-time; sub-agents return condensed summaries; persist structured notes outside the context. | Fresh session per stage; `locate` returns paths/symbols; `progress.md`. |
| Anthropic, *Claude Code best practices* | Explore → plan → implement → commit; every task has a runnable pass/fail check ("if you can't verify it, don't ship it"); for bugs write a failing test first, fix the root cause; review in a fresh subagent that sees only diff + criteria; specs name files/interfaces, out-of-scope, and an end-to-end verification step; after two failed corrections clear context. | Stage order; per-task gates; `reproduce`; `verify` design; `spec` format; fresh-session retries. |
| Anthropic, *Writing tools for agents* | Few consolidated tools; truncate outputs; errors state specific, actionable improvements; track tool-error and redundant-call rates. | Gate messages are specific (test id, path, exit code); driver records `tool_errors` per call for harness-health reporting. |
| Anthropic, *Harness design for long-running apps* (2026-03) | Separate generator from evaluator; sprint contract before code; evaluator drives the running system, scores per criterion with hard thresholds; calibrate the evaluator with few-shot scored examples; structured handoff files on context resets; remove components one at a time. | `verify` fresh + hard thresholds; `spec` before code; verifier calibration on dev set; `progress.md`/`state.json`; ablations. |
| GitHub Spec Kit, *existing projects* / *spec-driven* | Derive the constitution from evidence, don't invent standards; spec the change, not the whole system; state compatibility boundaries; plan must confirm reuse of existing architecture, deps and test conventions; mark ambiguities `[NEEDS CLARIFICATION]`; tests written and failing before implementation. | `map` = evidence only; `spec` scope + compatibility; `plan` must reuse map conventions (**gate `modules_and_tasks_known`**); interactive open questions; `reproduce`. |
| BMAD brownfield guide | Document the project first and review the output; for large codebases document only relevant areas; architecture must cover integration strategy, compatibility and risks; scale ceremony to change size; risk assessment right after story creation; regression tests for existing functionality; every touched legacy module needs tests; every change has a rollback plan; risky changes behind toggles. | `map` reviewed by a human once per repo (Phase 6 step 7: fix the prompt, never the map); `locate` scopes; `spec` risks; `plan` rollback section; feature toggles only if the codebase already uses them; `intake` records `size` and `pipeline.yaml: small_change_skips` lets a deployment scale ceremony (the benchmark keeps it empty). |
| AWS Kiro specs | EARS syntax for ACs; bugfix spec = current / expected / **unchanged** behaviour; design has root-cause analysis and properties to test; tasks prove the bug reproduces, the fix works, unchanged behaviour holds; analyze requirements for inconsistencies before design; keep specs small and in the repo. | EARS criteria; "Unchanged behaviour" section; `locate` root-cause evidence; `reproduce` + `repro_tests_pass_from_fixing_task` + verify regression check; spec gate checks criteria consistency (ids unique, each verifiable); `.s2a/runs/<id>/spec.md` in the repo. |
| Feathers, *Working Effectively with Legacy Code* | Change algorithm: identify change points → find seams/break dependencies → write tests → change → refactor; characterization tests record actual behaviour; sprout method/class, wrap method; scratch refactoring then revert. | `locate` (change points, seams; read-only), `reproduce` (characterization), `plan` approach field. Scratch refactoring to learn code is not a stage of its own: `locate` reads, and any stray edit by a read-only stage is reverted by the `clean_tree` check — the "then revert" half of the technique is enforced. |
| Fowler, strangler fig / preparatory refactoring / legacy modernization with GenAI | Replace at seams incrementally; "make the change easy, then make the easy change"; one hat at a time (refactor commits keep behaviour, then a separate behaviour change); scaffold new steps as no-ops; understand existing behaviour bottom-up before changing; add tests as a safety net first; treat LLM output as a draft; some questions need runtime analysis. | `plan` preparatory tasks; commit separation; `reproduce` safety net; `verify` as the review of a draft; runtime analysis **deferred** (v1 has no emulator/runtime). |
| Agentless | Hierarchical localization; LLM ranking + retrieval; only keep repro tests that fail on the original; select patches by regression tests then repro tests; only ~44 % of generated repro tests were correct — validate them. | `locate` hierarchy; `repro_tests_behave` gate; verify runs regression then repro. |
| SWE-agent | Lint-reject bad edits; moderate file windows beat whole files; summarize search output; collapse old observations; fail fast after a failed edit. | Optional lint gate; render caps; fresh-session retries; bounded retries. |
| TestPrune | Prune the regression suite to the relevant subset (+8–13 % resolution). | Regression subset = tests from `locate` + affected modules; whole-repo test runs are not required by gates. |
| SWE-Doctor | One repro test per behavioural requirement; feed runtime diagnosis records (test output), not raw tests, to the fixer; never target fail-to-fail tests. | `reproduce` prompt; `fix` receives the verifier's evidence; gates distinguish assertion failures from compile errors. |
| FEA-Bench | Feature tasks need new components plus edits elsewhere; more context lowered resolution; edit format matters; resolution falls as the number of new functions rises — split features. | `plan` splits features into tasks that each add few new units; render caps. |
| SWE-bench Multimodal | UI issues need visual evidence in the input. | **Deferred**: v1 grades JVM tests only; UI screenshot evidence is a v2 item. |
| Aider repository map | Map from tree-sitter definitions/references, graph-ranked, capped (~1k tokens); signatures only; re-rank per task. | `map` central files ranked by references (evidence: import/usage counts); `locate` re-ranks for the ticket; a tree-sitter-based map generator is a v2 improvement (v1 lets the agent build the map with grep). |
| Google SWE book ch. 9 / small CLs / Hyrum's law | ~200-line changes; one issue per change; refactorings in separate CLs; include tests with the change; each step keeps the build working; all observable behaviour is depended on. | `plan` task size and separation; commit per task with tests; verify treats unspecified behaviour changes as regressions. |
| Android testing strategies / Robolectric guidance | Use the lowest pyramid layer that gives the needed feedback; Robolectric when code depends on Android classes; UI/system tests need devices. | `profiles/android.yaml` notes; prefer plain JVM tests, Robolectric for Android-dependent code; device tests deferred. |

## Deferred (and why)

- Runtime/dynamic analysis and emulator-driven verification (Fowler, Android): no device in v1.
- Visual evidence for UI issues (SWE-bench Multimodal): v2 with screenshot tests.
- Tree-sitter/graph-ranked map generation (Aider): v1 map is agent-written and gated; a
  deterministic generator is a Phase 6 stretch item.
- Automatic feature flags for risky changes (BMAD): only when the codebase already has a
  flag mechanism; otherwise out of scope for a change request.
